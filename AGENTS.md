# Smartgram: правила разработки и публикации

## Сервер и рабочие каталоги

- `ssh smartgram` → обычный пользователь `smartgram-dev`, dev-копия `/opt/smartgram/dev`.
- Production: неизменяемые Git-релизы `/opt/smartgram/releases/<commit>`; `/opt/smartgram/current` — активная ссылка.
- Панель остаётся в `/opt/smartgram-panel/current`; службы `smartgram-panel` и `smartgram-panel-proxy`.
- Новые производственные данные: `/var/lib/smartgram`, очередь/история панели: `/var/lib/smartgram-panel`.
- Исходные перенесённые данные: `/var/lib/smartgram/imported/mac-project`, закрытые и неизменяемые.
- Dev-тесты и результаты: `/var/lib/smartgram-dev`, отдельно от production.
- Секреты: `/etc/smartgram/production.env`; аккаунт сайта: `/etc/smartgram-panel/config.json`. Не печатать значения и не включать в Git/архивы.
- Mac-исходники и медиа сохраняются. Старые абсолютные пути разрешает `server_import.py` по `/etc/smartgram/import-paths.json`; историю не переписывать.

## Проверки и выпуск

Production-файлы напрямую не редактировать. Обычная правка не запускает TTS,
ASR, исследование, поиск или генерацию картинок и полный прогон без необходимости.
Не менять голоса, модели, визуальную политику, лимиты и проверки принятых файлов.

```bash
cd /opt/smartgram/dev
# подходящие офлайн-проверки без сети:
/opt/smartgram/python-env/bin/python server_infra/check.py
# После коммита — проверка и публикация конкретной ревизии:
sudo /usr/local/sbin/smartgram check
sudo /usr/local/sbin/smartgram deploy "$(git rev-parse HEAD)"
sudo /usr/local/sbin/smartgram status
sudo /usr/local/sbin/smartgram rollback
```

`check` отказывается от незакоммиченных изменений. Публикации взаимно исключены;
deploy проверяет ревизию, использует drain, ждёт активное задание и сохраняет
ожидающие. Откат меняет код и совместимые runner-поля, а не пользовательские данные.
При ошибке восстановления очередь остаётся на паузе. Не вызывать старые
`web_analytics/publish.py`/панельный installer поверх подключённого конвейера:
их прежний restart не реализует ожидание активной задачи.

Шрифт измерения и рендера — фактически проверенный Arial в `/opt/smartgram/fonts`.
Один ролик одновременно, `SMARTGRAM_FFMPEG_THREADS=1`. Не запускать несколько
тяжёлых рендеров или проверок одновременно. Не менять тариф сервера.

Краткий итог: изменения, проверки, реальные блокеры. Большой HTML и сверку
биллинга не создавать при обычной правке. ZIP/review — только по явному запросу
или в существующем отдельно запрошенном процессе внешнего ревью. Старый локальный
процесс Mac сохранён в `LOCAL_REVIEW_WORKFLOW.md`; применять его только при таком
запросе. На Linux не создавать фиктивные Mac-пути и не устанавливать Drive Desktop.

## Ассоциативный видеоряд и резерв генерации (актуальная политика)

Для текущего MVP visual — красивый тематический видеоряд, не доказательство речи.
Согласовывай строки всех активных визуальных промптов и JSON-копий; факты речи
остаются строгими. Используй role=illustrative, обычно пустые must_show/must_not_show,
широкие запросы и полноценный crop 9:16 без полей. Не требуй схем и точной эпохи/вида.
Pexels — необязательный первый источник в FastMaterials, Wikimedia — резерв.
Ключ PEXELS_API_KEY только локальный; без него сразу Commons, не проси ключ в чате.
Не обходи квоту и не копируй каталог. Лицензия Pexels отличается от Commons.
Старые одобрения/схемы не доказывают работу новых промптов: для проверки нового
визуального запуска можно переносить только неизменённые текстовые привязки.

Последним уточнением пользователь сохранил генерацию красивых картинок как резерв
после неудачного поиска. Разрешил ТОЛЬКО для сгенерированных иллюстраций размер
1024×1536 и увеличение на 25% до 1280×1920 с последующим штатным crop 1080×1920,
без полей. Сохраняй native-исходник, SHA и запись преобразования в происхождении.
Фотографии, общие бюджеты и геометрические проверки не ослабляй. Модель/quality/n,
ограниченные попытки и отсутствие автоматических повторов API сохраняются.
Одна финальная сборка с курируемым review и штатной передачей; большой HTML и
Costs API в быстром визуальном запуске не обязательны.

## Монтаж готовых материалов без повторов (2026-11-01)

В одном ролике исходник занимает один непрерывный визуальный участок. ID поставщика
и хеш исходника до кропа определяют идентичность; смена имени/кропа/зума её не меняет.
Будущий подбор исключает занятые источники во всех фрагментах, кеше, импорте и resume,
но разрешает собственное назначение и общий кеш между роликами. Неудача не резервирует
изображение и не создаёт глобального запрета. При монтаже старых материалов соседние
повторы объединяются; возврат A,B,A продлевает B. Весь звук, текст и привязки остаются.
Новый montage_plan.json хранит покрытые shot_id/fragment_index и проходит финальную
проверку, а не присваивает себе старое одобрение.

Для явного набора готовых входов используй production_batch.py --inputs-file JSON
--output ПАПКА. Маркер assembly_inputs.json запрещает поиск/генерацию при ремонте.
Готовые проверенные темы не пересобирай из-за исправления другой темы. Разметку
субтитров и silent.mp4 можно восстановить только по совместимым входам/хешам;
модельные лимиты не обнуляются. Локальные переносы используют реальные метрики
шрифта; разделение блока допустимо только на подтверждённой границе слов без
изменения таймкодов и ослабления ограничений.

MP4 передавай отдельно от исходникового ZIP через release_sync.sync_videos:
проверенный существующий Drive-каталог, новая папка версии, атомарные копии,
размер/SHA-256, компактный assembly_status.json с атрибуцией. Прежние версии сохраняй.
Не копируй outputs целиком и не заявляй подтверждённую облачную загрузку.
