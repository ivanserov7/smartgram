# Smartgram

## Визуальные материалы и монтаж — объединённая реализация

Код перенесён из проверенной отдельной копии в основной проект с трёхсторонним
сравнением исходного снимка. Текущие озвучка Gemini и аналитика сохранены.
История интеграции и резервные копии — в `.isolated/integration_20261101T125231Z`.

Обычный `main.py` теперь выполняет пять шагов материалов, затем пять шагов
монтажа. Поиск начинается после принятия сценария, независимо от WAV. Если
озвучка изменила сценарий, перед монтажом визуальные привязки проверяются заново;
неизменённые фрагменты используют прежние результаты. Исторические команды
`visuals.py`/`visual_review.py` сохранены для чтения старых результатов и не
являются новым этапом подготовки кадров.

| Модули | Работа |
| --- | --- |
| `visual_materials.py` | visual_queries → visual_search → visual_select → visual_prepare → visual_review; оригиналы, лицензии, версии, постоянные бюджеты |
| `visual_geometry.py` | Ориентация EXIF, crop/background без увеличения, геометрия всего пути, одни преобразования превью и видеокадров |
| `editing_inputs.py` | Проверка одобренных входов, снимки зависимостей, импорт нового аудиоманифеста без генерации |
| `editing.py`, `video_render.py` | video_render → subtitle_segment → subtitle_layout → compose → final_check; готовность требует полного decode и всех партий кадров |
| `subtitles.py`, `video_schedule_check.py` | Полное покрытие токенов/слов, метрики настоящего шрифта и libass, сравнение фактических кадров с ожидаемой композицией и ASS |
| `video_music.py` | Необязательный локальный разрешённый трек, SHA-256, атрибуция, ослабление и ducking; по умолчанию выключен |
| `production_state.py` | Постоянные операции и бюджеты, блокировка одновременных команд, существующий OpenAIMeter |
| `production.py`, `visuals_only_batch.py`, `production_batch.py`, `production_report.py` | Запуск готовых входов/resume, три темы и чистый автономный HTML без общей синхронизации |
| `visuals_editing_config.json`, `prompts/visual_*.txt`, `prompts/subtitle_segment.txt`, `prompts/final_check.txt` | Полный контракт и несокращённые промпты из приложения к задаче |

Запуск из готового сценария с сохранением входов в отдельной папке:

```bash
.venv/bin/python production.py --script-file /ПУТЬ/К/ПРИНЯТОМУ/script.json --run-dir outputs/МОЙ_ЗАПУСК --stage visuals
```

Отсутствие WAV не мешает поиску. Необходимы `script.json` и одобрение той же
версии в `script_state.json`. Это платные вызовы OpenAI и бесплатный Commons;
исследование, сценарист, Deepgram и TTS здесь не вызываются.

Продолжение, включая готовый аудиоманифест из другой папки:

```bash
.venv/bin/python production.py --resume outputs/МОЙ_ЗАПУСК --audio-manifest /ПУТЬ/audio_manifest.json --stage editing
.venv/bin/python production.py --resume outputs/МОЙ_ЗАПУСК --stage all
.venv/bin/python main.py --resume-production outputs/МОЙ_ЗАПУСК
```

Для уже принятых материалов из другой папки можно добавить
`--materials-file /ПУТЬ/visual_materials.json --stage editing`. Импорт копирует
оригиналы/превью либо WAV, проверяет хеши источника до и после копирования,
сохраняет исходный манифест, отображение путей и прежние входы в `input_history`.
Он не повышает статус одобрения. Изменение аудио или таймкодов создаёт новый
монтаж; поиск тех же изображений не требуется. Неизменённые успешные модельные
операции берутся из журнала. Незавершённая/неуспешная платная операция не
повторяется молча: списание может быть неизвестно. Сетевые повторы API — 0.

`--dry-run` доступен в обеих командах: он не читает входы и не вызывает API.
`--stage visuals` завершается ошибкой, если не все материалы приняты; подробные
причины и уже принятые фрагменты остаются в манифесте.

Контракт аудио соответствует существующему `voiceover.py`:
`mode=real`, `status=completed`, `audio_kind=ai_generated_speech`,
`text_verified=true`, `timing_status=aligned_to_deepgram_words`, проверка
`Можно использовать`, `script_version_id`, `audio_sha256`, `audio_path`,
`total_duration_seconds`, `words` с `word_id/start/end` и `fragments` с
**индексами от 1**, `first_word_id/last_word_id`, `speech_start/speech_end`,
`display_start/display_end`. Границы показа покрывают WAV от нуля до конца,
включая паузы. Времена слов не обрезаются, не растягиваются и не придумываются.
Визуальный манифест новой схемы — `visual_materials.json`, `schema_version=1`;
в нём нужны `approved` каждого фрагмента, оригиналы, их SHA-256, motion,
три реальных превью и точная атрибуция. Старое `selected` не считается этим
одобрением и не преобразуется в него автоматически.

Пределы: 5 пригодных кандидатов на фрагмент за раунд, 2 раунда, 6 поисковых
обращений на раунд с учётом continuation и неудачных обращений; 2 исправления
кадрирования на кандидата после первой подготовки, затем неиспользованный
резерв и оставшийся поиск. Неизвестная лицензия, отсутствие автора/точного URL
или неподтверждённые ограничения не обходятся. Поиск ограничивается bitmap;
MIME, размеры, EXIF, полное декодирование, дубли и лицензия проверяются кодом.
Оригинал не заменяется уменьшенным изображением, отправленным модели.
При изменении text/visual новый бюджет относится к новой версии затронутого
фрагмента; повтор команды или смена промпта старые бюджеты не обнуляют.

Геометрия: 1080×1920, 0–10% zoom. Проверяется самый тесный crop и весь линейный
путь; фон сохраняет целое переднее изображение и его настоящее разрешение.
Видеоряд по умолчанию 30 fps/cut. Необязательный dissolve смешивает кадры на
общей шкале, ограничивается половиной короткой сцены и не сокращает звук.
Непредставимо короткая сцена блокирует выпуск. Ни `-shortest`, ни изменения
темпа речи в активном коде нет.

Субтитры: точный исходный текст, существующие audio IDs, максимум 2 строки,
56 px на 1080, область 84%, отступ снизу 12%, 600–6000 мс, 22 знака/с.
Явно выбран установленный **Arial** вместо заводского DejaVu Sans:
`SUBTITLE_FONT_PATH=/System/Library/Fonts/Supplemental/Arial.ttf`, семейство
`Arial` в JSON. Используются этот файл, его SHA-256 и подтверждённое libass
PostScript-имя ArialMT. Проверяются Pillow-метрики и настоящая растровая область
libass с обводкой/подложкой. Другой шрифт не подставляется автоматически.
Эквивалентная токенизация учитывает е/ё, числа 0–999, т. е./т. д. и явный
словарь сокращений GPS/км/кг/см в конфигурации. Несколько текстовых токенов могут
соответствовать одному слову и наоборот в проверенном диапазоне фрагмента;
неоднозначные формы возвращаются на деление или блокируются с причиной.
`uncertain/blocked` допустимы без фиктивных cues. Группы исправлений привязаны
к фрагменту, поэтому новые cue ID не сбрасывают предел 2 исправлений.

Compose: MP4 H.264/AAC, yuv420p, CRF 20, faststart. Двухпроходный loudnorm
целится в −16 LUFS; запас true peak −2 dB перед AAC позволяет проверить
фактический предел ≤−1 dBTP после AAC. Допуск громкости ±0,5 LU задан в отчёте;
длительности — один видеокадр плюс 1024/48000 с AAC priming.
Финальная техническая проверка декодирует весь файл, проверяет потоки, кадры,
длительность, хеши и сравнивает извлечённые кадры с ожидаемой сценой и ASS на
реальном PTS. Модель получает кадры именно из `candidate.mp4`: начало,
середину, конец каждого cue и границы переходов. Все frame ID должны быть
проверены; пропуск, ошибка API или uncertain блокируют ready.

Смысловые замечания возвращаются к субтитрам или в существующий визуальный
этап с оставшимися бюджетами; новое кадрирование снова принимает visual_review.
Общий предел финальных исправлений — 2. Отсутствие сохранённого бюджета для
импортированного материала или однозначной безопасной коррекции останавливает
выпуск. Кадры не доказывают произношение, синхронизацию на слух или плавность
всего видео. Успех FFmpeg или HTTP сам по себе не означает приёмку.

Успешные выходы: `video.mp4`, `subtitles.srt`, `subtitles.ass`, `attribution.json`,
`quality_report.json`, `render_manifest.json`. До приёмки хранится только
`candidate.mp4`. Неуспех сохраняет причину, историю, входы, диагностику;
`blocked_upstream` означает, что готовый принятый вход отсутствует.
Телеметрия остаётся в `openai_usage.json` и читается существующим billing:
`stage`, `step`, run/call/model/usage/статус/время; локальный рендер и поисковые
обращения учитываются отдельно. Расходы не вычисляются по тарифам и остаются
null до распределения подтверждённой Costs API суммы.

Проверки без случайных платных запросов:

```bash
.venv/bin/python run_tests.py
.venv/bin/python editing_smoke.py --output outputs/МОЙ_ТЕСТ
.venv/bin/python editing_smoke.py --output outputs/МОЙ_DISSOLVE_ТЕСТ --transition dissolve
```

Smoke выполняет настоящий рендер 5 с/1080×1920/30 fps/150 кадров, decode,
измерение AAC, проверку кадров/subtitles, отрицательный тест повреждённого MP4
и resume. Сеть/DNS запрещены; изображения и звук синтетические, модельные
решения подставлены. Выход `test_video.mp4`, `test_passed`; `ready=false`.
Тестовые файлы не используются как принятые входы трёх реальных тем.

Актуальная официальная документация проверена перед платными вызовами:
[GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna),
[изображения](https://developers.openai.com/api/docs/guides/images-vision),
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Доступность конкретного аккаунта подтверждается только реальными вызовами;
модель и параметры не меняются при ошибке.

В основном проекте действует штатная передача по AGENTS.md: общий ZIP на
Desktop и версионная копия в проверенную папку Drive, HTML — через
`html_report_sync.py`. Прежнее исключение изолированной задачи отменено.
`production_report.build_report` остаётся чистой функцией; готовую страницу
нужно передать штатным механизмом. Команда ниже делает это автоматически:

```bash
.venv/bin/python visuals_only_batch.py --script-batch outputs/script_batch_tvuyecw6 --directory outputs/visuals_only_20261101
# Повтор той же команды продолжает сохранённые операции и бюджеты.
# Один готовый снимок без WAV и монтажа:
.venv/bin/python main.py --resume-production outputs/visuals_only_20261101/topic_1 --production-stage visuals
```

Галерея `Smartgram_visuals_only_<UTC>.html` автономная, с выбранными изображениями,
превью в нормированных точках 0/0.5/1, атрибуцией, решениями ИИ и попытками.
При общей ошибке доступа/квоты/сети запросы останавливаются; исходные причины и
остальные темы со статусом `not_started` сохраняются. Неудачная операция не
повторяется молча при продолжении. Пустой поиск продолжает независимые фрагменты
в оставшихся пределах, не превращает их в фиктивно готовые изображения.

Smartgram превращает тему в материалы для познавательного вертикального видео
на 30–45 секунд. Активная схема: исследователь → сценарист (написание текста
и визуального замысла + проверка с веб-инструментом) → озвучка и визуальные материалы →
монтаж → проверка и сохранение. Успешный сценарист использует ровно два запроса:
написание без веба, затем проверка с вебом. Отдельного ИИ-планировщика сцен больше нет.
Полная озвучка: Gemini gemini-3.8-flash-tts / Kore → Deepgram Nova-2 и независимый
OpenAI ASR → GPT-проверка текста и привязка фрагментов. Подбор Commons и Vision адаптированы к сценарию.
Готовность озвучки требует исправного WAV, проверенного текста, длительности
в диапазоне и полной привязки фрагментов. Новый путь неподвижных изображений, субтитров, монтажа и MP4 реализован в основном проекте. Отдельный `media_check.py` проверяет локальную среду монтажа
на синтетическом тесте; он не запускает конвейер и не означает готовность монтажа.
Gemini используется только для синтеза голоса; остальные модели конвейера не меняются.

## С чего начать

Откройте `main.py`: он читает аргументы и передаёт управление в `pipeline.py`.
В `pipeline.py` видна последовательность этапов и условия остановки.
Каждый основной этап находится в отдельном файле:

| `research.py` | Вход исследования, совместимость старых данных, сохранение JSON/Markdown |
| `research_engine.py` | Два этапа: веб-сбор фактов и оценка достаточности, накопление по раундам |
| `research_models.py`, `research_config.py` | Схемы формата 4, доступность, отдельные настройки исследователя |
| `prompts/research_*.txt` | Точные промпты этапов, отдельно от входных данных |
| `research_topics.json`, `research_batch.py`, `research_batch_report.py` | Постоянные три темы, последовательный запуск и общий подробный HTML |
| `research_requests.py` | Responses API без повторов и журнал точных моделей/usage |
| `research_evidence.py`, `research_validation.py` | Совместимость исторических результатов формата 3 |
| `research_report.py` | Автономный читаемый HTML-отчёт исследования |

## Запуск без ключа и без сети

Все команды выполняйте из папки проекта через существующее окружение `.venv`.
Для установки зависимостей (нужна сеть только для скачивания пакетов):

```bash
.venv/bin/python -m pip install -r requirements.txt
```

Только посмотреть план, не читая настройки и не создавая результатов:

```bash
.venv/bin/python main.py --topic "Почему закат красный?" --dry-run
```

Пройти этапы на подставных ответах:

```bash
.venv/bin/python main.py --topic "Почему закат красный?" --demo
```

`--demo` не вызывает API. Он проверяет исследование и сценариста на подставных
ответах, затем останавливается перед новым блоком озвучки. Для полного блока
речи есть офлайн-тесты с подменой API; они не создают настоящую речь.
Используется фиксированная учебная заготовка о закате, даже если указана другая
тема. Это проверка работы программы, а не настоящее исследование или проверка
фактов. Консоль, Markdown и JSON явно помечены; JSON содержит `mode: demo`,
проверка — `verification_kind: simulated` и `demo_passed` вместо `passed`.
Сохранённое тестовое исследование нельзя продолжить в реальном режиме.
Аудио в демонстрации — только тишина по 0,25 секунды на сцену, не речь.
Манифест помечен `mode: demo`, `audio_kind: test_silence`; тестовый кеш
не используется в реальном режиме.
Демонстрация подбора изображений не обращается к Commons: она сохраняет
`needs_visual`, без тестовых картинок, выдаваемых за настоящую находку.

Для проверки веток конвейера:

| Аргументы к `--demo` | Ожидаемое поведение |
| --- | --- |
| `--demo-case success` | Успешный тестовый проход с первой версии (по умолчанию) |

## Исследователь: ровно два смысловых этапа

**Этап 1 — поиск и сбор.** Один запрос Responses API получает тему, накопленные
факты/источники и `missing_questions`. Модель использует `web_search`: ищет,
читает необходимые части страниц, оценивает конкретные материалы и возвращает
утверждения с фрагментами, URL, названием и основанием выбора. Для науки
предпочтительны научные организации, университеты, исследования и качественные
образовательные материалы; язык поиска — русский и английский. Домен сам по себе
не гарантирует качество. Обязательной загрузки статей Python нет.

**Этап 2 — оценка полноты.** Отдельный запрос без инструментов получает тему и
весь накопленный материал. Ответ содержит ровно два поля: `enough` и
`missing_questions`. В интерфейсе `true` — **«Хватает»**, `false` — **«Не хватает»**.
При `true` список вопросов пуст, при `false` содержит конкретные пробелы.
Это оценка полноты для объяснения на 30–45 секунд, а не независимая проверка истинности.

При «Не хватает» разрешён один дополнительный раунд: новый сбор получает
конкретные вопросы. Полезные факты, фрагменты и оговорки первого раунда сохраняются;
дополнения добавляются, противоречия не скрываются. Максимум два раунда на тему,
при готовности завершение раньше. Между сбором и оценкой нет дополнительных
модельных вызовов. Ошибка API, незавершённый ответ или неверный JSON — **сбой
выполнения**, а не третий вердикт и не «Не хватает»: `enough` остаётся `null`.

Одного качественного источника достаточно для прямо подтверждаемого утверждения.
Нет минимального числа фактов, требования двух источников или фиксированного числа
страниц. Python проверяет формат, обязательные поля и допустимость HTTP(S)-URL;
не проверяет совпадение цитат и нумерацию абзацев. Старые пороги форматов 2/3
не применяются к новому исследователю.

Формат 4 хранит `statement` и вложенные `evidence`: `url`, nullable `title` и
`excerpt`, `source_reason`, `availability`, `availability_details`, `excerpt_kind`.
Доступность — **заявление модели**: `page_text`, `partial_text`,
`search_description`, `unavailable` или `unknown`. Только сниппет, недоступный,
неизвестный или отсутствующий фрагмент сохраняется отдельно как неподтверждённый
кандидат. Фрагмент не называется автоматически проверенной дословной цитатой.

Раскрытые API поиски/открытия/источники хранятся отдельно от слов модели.
Наличие ссылки или заявления «я открыл» не становится подтверждённым чтением.
Даже раскрытый `open_page` не доказывает успешное получение текста; нераскрытые
поля записываются как `null` с пояснением. Полные тела запросов и ответов,
usage и время сохраняются без ключей и заголовков авторизации.

## Полная озвучка: Gemini TTS → две ASR → OpenAI

Рабочие defaults: **gemini / gemini-3.8-flash-tts / Kore**. Синтезатор выбирает
`voice_factory.py`; автоматического возврата к OpenAI при ошибке нет. Исследователь,
сценарист, поиск изображений и монтаж на Gemini не переводятся.

Нужны `GEMINI_API_KEY`, `DEEPGRAM_API_KEY`, `OPENAI_API_KEY` в локальном `.env`.
Ключи никогда не входят в JSON настроек или отчёты. Ключ Google можно получить
в https://aistudio.google.com/api-keys — не присылайте его в чат. Переменные
окружения приоритетнее `.env`; перед реальным запуском проверьте фактические
`VOICE_TTS_PROVIDER`, `VOICE_TTS_MODEL`, `VOICE_TTS_VOICE`. Админский ключ OpenAI
остаётся только для Costs/Usage.

Четыре пользовательских шага:

1. **Синтез.** Один запрос Google Interactions читает весь `narration_text`, который
   соединяет только `fragments[].text`. `visual`, названия сцен и инструкции не
   произносятся. `VOICE_TTS_STYLE` передаётся отдельно как `speech_metadata.style`,
   голос — в `generation_config.speech_config`. Готовый WAV сохраняется напрямую,
   без второго RIFF и без предположения о частоте 24 кГц.
2. **Две независимые расшифровки.** Nova-2/ru даёт слова/секунды. OpenAI
   gpt-transcribe всегда независимо получает тот же WAV, без подсказки сценария.
   Обе операции привязаны к SHA-256 WAV, модели и параметрам; ошибку ASR не считают
   ошибкой диктора и не исправляют синтезом.
3. **GPT-проверка текста и привязка.** gpt-6-luna/low получает сценарий, обе ASR
   и word_id Deepgram. OpenAI ASR — основной источник подтверждения текста.
   Полное совпадение OpenAI со сценарием после регистра, пунктуации и ё/е
   принимается в Python даже при ошибочном отрицательном GPT-вердикте.
   Числа, знаки, отрицания и смысловые различия не стираются; в остальных
   случаях GPT содержательно сравнивает OpenAI со сценарием. Ошибка Deepgram
   не отменяет подтверждение OpenAI, не требует нового TTS и не оставляет
   текст в needs_review. Контракт v2 и сравнение обеих ASR сохранены.
   Индексы, цитаты, полное покрытие и фактические времена слов проверяются
   независимо; alignment_error означает проблему привязки при принятом тексте.
   При плохом JSON разрешена одна дополнительная GPT-проверка с конкретным
   замечанием, без нового TTS и ASR. Второй плохой контракт останавливает шаг.
   Секунды берутся только из Deepgram, не обрезаются и не растягиваются. Внутри
   этого же шага создаются speech/display-интервалы от 0 до полной длительности
   с паузами; отдельного пятого шага нет.
4. **Результат.** Сначала подтверждается текст, затем проверяется фактическая
   длительность 30–45 с. В обычном pipeline при верном тексте и неверной длине
   используется общий оставшийся бюджет сценариста. Подтверждённая существенная
   ошибка чтения может вызвать только ограниченный повтор синтеза; неопределённость
   останавливает работу без переозвучки. Качество русского звучания отдельно
   ожидает прослушивания пользователя.

Только сохранённый сценарий, без исследования и картинок:

```bash
.venv/bin/python main.py --script-file outputs/ПАПКА/script.json
.venv/bin/python main.py --script-file outputs/ПАПКА/script.json --dry-run
```

`--scenes-file` сохранён как вход совместимости: озвучивается связанный целый
одобренный сценарий. Полный pipeline может остановиться после голоса:

```bash
.venv/bin/python main.py --research-file outputs/ПАПКА/research.json --stop-after voiceover
```

Партия последних одобренных сценариев:

```bash
.venv/bin/python voiceover_batch.py --script-batch outputs/script_batch_tvuyecw6
```

Идентичность партии теперь включает провайдера, модель, голос и стиль: старый
отчёт OpenAI не перезаписывается новой партией Gemini. `--resume` явно продолжает
указанную папку, сохраняя её историю. Исходные сценарии и их бюджет не обнуляются.

Повторить проверку уже сохранённого WAV, не вызывая синтез или сценарист:

```bash
# Переоценить по сохранённым двум ASR/GPT и актуальному WAV, строго без API:
.venv/bin/python voice_recheck.py --run-directory outputs/ПАПКА --local-only
# После локальной переоценки обычный повтор использует проверенный результат:
.venv/bin/python voice_recheck.py --run-directory outputs/ПАПКА
# Явно оплатить новый раунд ASR/GPT по тому же звуку (максимум 2 дополнительных):
.venv/bin/python voice_recheck.py --run-directory outputs/ПАПКА --new-asr-round
```

При ошибке времени/сервиса этот путь оставляет исходный WAV неизменным. Для
дословно изменившегося сценария старый WAV не применяется. Технические ошибки
429/5xx и соединения имеют ограниченные повторы с backoff, по умолчанию один;
аутентификация, billing/insufficient_quota и недоступная модель не повторяются.
Google SDK получает attempts=0, OpenAI SDK max_retries=0. В google-genai 2.34
ноль преобразуется в единицу и Interactions трактует её как повтор: поэтому
HTTP-ошибка перехватывается после записи ответа до повторов SDK, а request-hook
запрещает второй HTTP в одном раунде. Повторами управляет только внешний цикл;
каждый отправляемый HTTP фиксируется в attempts/http_request_count. Billing,
нулевая и суточная квота не повторяются. Таймауты также учитываются отдельными
попытками. После перезапуска незавершённый/неудачный исход
автоматически не повторяется: для ASR нужен явный новый раунд.

### Настройки и результат

`VOICE_TTS_PROVIDER=gemini`, `VOICE_TTS_API=interactions`,
`VOICE_TTS_MODEL=gemini-3.8-flash-tts`, `VOICE_TTS_VOICE=Kore`,
`VOICE_TTS_STYLE` и `VOICE_TTS_ADAPTER_VERSION` задают синтез. Указанный в старом
`VOICE_NARRATOR_PROMPT_FILE` текст используется только для явно выбранного OpenAI;
Gemini получает именно отдельное поле style. Актуальный google-genai **2.34.0**
закреплён в `requirements.txt`, проверен в существующей `.venv`.

Ключ генерации учитывает провайдера, модель, голос, точный текст, style,
версию адаптера и формат. Старый WAV OpenAI не является cache hit Gemini.
Смена промпта проверки не вызывает новый TTS, ASR/проверки привязаны к хешу
нового WAV. Успешное возобновление не оплачивает этапы повторно.

`audio_manifest.json` сохраняет прежний schema_version=3 и имена выходов:
`audio_path`, `audio_sha256`, `duration_seconds`, `frame_count`, фактическую модель,
голос, стиль, MIME, sample_rate/channels, usage и request/response ID, если сервис
их вернул. Сохраняются первоначальный `provider_audio.wav` и итоговый `audio.wav`;
их байты не ресемплируются и не переоборачиваются. Метаданные проверяются по
реальным WAV-кадрам; тишина, обрыв и клиппинг отмечаются отдельно. Если когда-либо
потребуется ресемплинг, это должен быть отдельный файл с настоящей конвертацией.

`voiceover_state.json` хранит операции и попытки, `voiceover/*/` — WAV/PCM,
сырой Deepgram, OpenAI transcript, все GPT-вердикты и ошибки их контракта.
`fragments` содержат принятые интервалы, `provisional_fragments` — предварительные
для просмотра при неуверенном/отклонённом тексте. Их нельзя считать готовым монтажом.
Gemini пишет `gemini_usage.json`, OpenAI — `openai_usage.json`, Deepgram —
`deepgram_usage.json`. Расчёты по usage — оценки, подтверждённые суммы не выдумываются.
Gemini не отправляется в OpenAI Costs API; тариф Deepgram пока не задан.

Отдельная короткая проверка выбранного голоса:

```bash
.venv/bin/python tts_check.py --text "Проверка русского голоса." --output-dir outputs/НОВЫЙ_ОБРАЗЕЦ
```

Для Gemini-образца нужен только Google-ключ. Это диагностический WAV, не
одобренный результат всей проверки. Старые файлы не перезаписываются.

`voiceover_report.py` открыто показывает provider/model/voice/style, три плеера
партии, текст, обе ASR, замечания, интервалы и статус «Качество русского звучания:
ожидает прослушивания пользователя». Внешний сайт здесь не публикуется; точный
JSON изменений для другого интерфейса — `external_voiceover_changes.json`.

Документация: [Gemini 3.8 Flash TTS](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash-tts),
[схема TTS](https://ai.google.dev/gemini-api/docs/speech-generation),
[тарифы Google](https://ai.google.dev/gemini-api/docs/pricing),
[устаревающие модели](https://ai.google.dev/gemini-api/docs/deprecations/).
Старый `gemini_tts.py` сохранён для исторических запусков по сценам; новый
`gemini_voice.py` использует тот же проверенный unary-паттерн и возвращает полную
метаинформацию. Ранее выполненные эксперименты OpenAI ниже оставлены как история.

## Исторический двухшаговый подбор Commons (команды совместимости)

Для отдельного подбора не нужны ключи OpenAI или Deepgram. Озвучка не запускается:

```bash
.venv/bin/python visuals.py --scenes-file outputs/ИМЯ_ПАПКИ/scenes.json
```

В основном CLI есть такая же команда:

```bash
.venv/bin/python main.py --visuals-file outputs/ИМЯ_ПАПКИ/scenes.json
```

Замените `ИМЯ_ПАПКИ` на свою папку запуска. `--visuals-file ... --dry-run`
показывает действие без чтения файлов и сети; `--demo` сохраняет только
потребность в визуале, не выполняя поиск. Модуль `visuals.py` не импортирует
OpenAI или Deepgram. Эти команды оставлены для старых манифестов; полный конвейер использует visual_materials.py и начинает поиск независимо от озвучки.

План должен содержать список `scenes`: у каждой сцены нужны уникальный
положительный `id`, непустые `search_query` и `visual_description`, а также
`material_type` со значением `image` или `video`. Необязательный `title`
участвует в оценке соответствия. Этот этап сам по себе не проверяет факты
сценария и не объявляет весь ролик проверенным.

Для каждой сцены типа `image` выполняется один запрос к официальному
`https://commons.wikimedia.org/w/api.php`: до пяти файлов из пространства
File, с `imageinfo` и `extmetadata`. Ключ API не нужен. Запросы последовательные,
с информативным User-Agent и без автоматических повторов. Поиск дословно
использует `search_query`; обычно полезны конкретные английские слова, потому
что значительная часть названий и описаний Commons написана на английском.
Программа не переводит запросы и не заменяет их более общими при неудаче.
Можно задать `WIKIMEDIA_USER_AGENT` в локальном `.env`, указав собственный
действительный контакт, как рекомендует [политика Wikimedia User-Agent](https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_User-Agent_Policy).
Шаблон закомментирован в `.env.example`. Используйте ASCII без переносов;
ключи API для Commons не нужны. С настроенным User-Agent с реальным контактом
контрольный запрос и поиск трёх сцен прошли успешно; результаты описаны ниже.

Фильтр лицензий намеренно узкий: распознаются CC BY и CC BY-SA версий
1.0/2.0/2.5/3.0/4.0, CC0 1.0 и Public Domain Mark 1.0 с явной ссылкой.
Название должно соответствовать распознанной ссылке Creative Commons.
Ссылки на локализованные страницы вида `/deed.en` или `/deed.ru` также
распознаются; исходный адрес сохраняется без изменений.
GFDL, неизвестные лицензии, отсутствие ссылки или автора, а также другие
неподдержанные условия приводят к пропуску. Это может исключить пригодный
файл, но программа не предполагает, что любой файл Commons можно использовать
без условий. Для выбранного изображения сохраняются автор, название,
страница файла, исходный URL, лицензия и её URL, credit, UsageTerms,
AttributionRequired и Restrictions, если они предоставлены API.

Перед публикацией необходимо просмотреть страницу файла и условия лицензии:
например, CC BY требует атрибуции, а CC BY-SA может потребовать соблюдения
ShareAlike для адаптации. Манифест содержит заготовку атрибуции и флаг
`requires_license_review: true`; это не автоматическое разрешение на публикацию.
Исходные изображения сохраняются без редактирования; последующие изменения,
включая кадрирование, потребуется учитывать при подготовке атрибуции.

Оценка соответствия сравнивает слова запроса, названия и описания сцены со
словами названия и описания файла. Требуется совпадение хотя бы 35% значимых
слов запроса; при недостаточном совпадении картинка не используется. При
равенстве оценки предпочтение получает большее полезное разрешение для 9:16
по метаданным. Это простой предварительный фильтр, без распознавания того,
что действительно изображено. В `reason` сохраняется объяснение выбора,
а в исходном `visual_manifest.json` поле `visual_check_status` остаётся
`not_performed`: проверка картинки выполняется отдельным этапом ниже.

Скачиваются только JPEG/PNG с серверов изображений Commons. Превью запрашивается
с официальных доменов `upload.wikimedia.org` и `thumb.wikimedia.org`. Второй
используется для новых превью; посторонние домены по-прежнему запрещены.
Изображение запрашивается
с шириной 2560, но реальные размеры проверяются после загрузки. Pillow проверяет
структуру и полностью декодирует файл. Минимум — 720×1280 с учётом EXIF-поворота:
это позволяет получить кадр 9:16 без увеличения. Горизонтальная фотография
должна иметь высоту хотя бы 1280. Пределы: 10 МиБ на изображение, 40 млн пикселей,
2 МиБ на ответ API, HTTP-таймаут 15 секунд и контроль времени потоковой загрузки
30 секунд. Анимации и другие форматы не поддерживаются. Если первый кандидат
повреждён или не проходит технические условия, проверяется следующий подходящий кандидат.
Ошибка сети или HTTP останавливает этап с сохранением причины, без нового поискового запроса.

Файлы сохраняются в `visuals/` рядом с планом. `visual_manifest.json` содержит
по каждой сцене результат, запрос, рассмотренных кандидатов с причинами
отклонения, выбранный файл, его SHA-256, размеры, атрибуцию и объяснение выбора.
`selected` означает только предварительный выбор. Если изображения нет, статус
сцены — `needs_visual`, без случайной подстановки. Для `material_type: video`
сохраняется `video_not_implemented`; изображение вместо него не выбирается.
Общий статус — `ready_for_visual_review`, если все сцены получили изображения,
иначе `needs_visual`. Код `0` означает, что манифест сохранён; наличие картинки
проверяется по статусам, а не по коду завершения.

При повторении той же команды уже выбранный файл используется без сети,
если не изменились запрос, название/описание сцены, тип материала и версия
подбора. Он заново открывается и сверяется по контрольной сумме и лицензии
из сохранённых метаданных. Повреждённый файл вызывает новый поиск и загрузку.
Успешный выбор имеет отдельную JSON-квитанцию в `visuals/`; она позволяет
восстановить потерянный общий манифест. Уже выполненные раунды хранятся в
`visual_manifest.json`: продолжение не обнуляет лимит. После сетевой ошибки
автоматического повтора нет; сохранённая причина требует отдельного разбора.

В первых реальных тестах API возвращал HTTP 403 с указанием robot policy.
После настройки User-Agent с настоящим контактом контрольный запрос вернул
HTTP 200. Три запроса `red sunset sky`, `Roman Colosseum`, `emperor penguin`
дали 15 кандидатов и три выбранных изображения. Поддержка нового домена
превью и локализованных страниц CC0 исправлена по этим реальным ответам.
Результат: `outputs/commons_three_scene_review_caogjys3/visual_manifest.json`.
Платные API и озвучка в проверке не использовались.

## Визуальная проверка OpenAI

Раньше выполнялся только подбор по метаданным. Теперь отдельный этап
`visual_review.py` передаёт сами JPEG/PNG в Responses API как Base64 `input_image`,
вместе с `narration` и `visual_description` сцены. Используется текущий
`OPENAI_VISION_MODEL` из `.env` (если не задана — `OPENAI_MODEL`),
`detail: high`, Structured Outputs и `max_retries=0`.
Названия файлов и поисковые описания модели не передаются: она видит только
текст сцены, номера кандидатов и изображения. Тексты на изображениях не должны
трактоваться как инструкции.

Отдельная проверка без исследования, озвучки и всего конвейера:

```bash
.venv/bin/python visual_review.py --scenes-file outputs/ИМЯ_ПАПКИ/scenes.json --scene-id 1
```

Рядом должен находиться `visual_manifest.json` с результатами Commons.
`--scene-id` ограничивает запуск одной сценой; без него проверяются все сцены.
Также доступно `.venv/bin/python main.py --review-visuals-file outputs/ИМЯ_ПАПКИ/scenes.json`.
У основного CLI есть `--dry-run`; `--demo` не вызывает API и не имитирует
успешное распознавание. Полный реальный конвейер теперь вызывает этот этап
после подбора Commons.

Новый запрос Vision платный: до шести изображений и не более 20 МиБ суммарно.
Повторы SDK отключены. При неизменных сцене, файлах и настройках используется
локальный кеш `vision_cache/`, без нового запроса. Ключ включает narration,
visual_description, идентификаторы и SHA-256 оригиналов и превью, модель,
параметры API, JSON-схему, версию и текст промпта, технические ограничения.
До чтения кеша файлы открываются заново, проверяются лицензия, атрибуция,
целостность, формат, разрешение, размер и хеш. Ошибки API не кешируются как
успешные проверки. В `vision_usage.json` сохраняется история реальных запросов
и полученный usage, включая неудачные ответы. При попадании в кеш в отчёте
`cache_hit: true`, `request_count: 0`, `usage: null`; исходный расход остаётся
в истории и `original_usage`, повторно он не начисляется.

Для ИИ из допустимого оригинала всегда создаётся одинаковое JPEG-превью:
EXIF-поворот, сохранённые пропорции, без обрезки, длинная сторона до 1024 пикселей,
качество 90, белая подложка для прозрачности. Превью находятся в `vision_previews/`,
полноразмерные файлы для монтажа — отдельно в `visual_originals/`.
`gallery_previews.json` никак не влияет на вход проверки. Недопустимые файлы
и изображения с неизвестной лицензией не отправляются для выбора.
Положительная оценка ИИ не отменяет ограничения лицензии, формата и разрешения.
Кандидата с неизвестной лицензией можно увидеть в отчёте, но нельзя выбрать
для ролика. Рисунки, музейные объекты, похожие виды животных и неуверенные
определения должны отклоняться, если они не отвечают тексту сцены.

Для каждой картинки модель возвращает описание видимого содержимого,
`suitable`/`unsuitable`/`uncertain`, оценку 0–100 и объяснение по-русски.
Выбор допускается только среди `suitable` с оценкой не ниже 75 и после
локальных проверок файла/лицензии. При равенстве оценки учитывается разрешение.
Если подходящих нет, сохраняется `needs_visual`, без случайной подстановки.
Пропущенные, повторённые или неизвестные номера кандидатов делают весь
ответ непригодным для выбора. Неполный ответ также не принимается.

Если поиск пустой, все кандидаты отсеяны локально (Vision не вызывался)
или ИИ отклонил всех допустимых кандидатов, OpenAI один раз
предлагает другой запрос с учётом сцены и причин отказа. Затем выполняются
новый поиск Commons и проверка изображений. Максимум **два раунда поиска на
сцену суммарно**, включая первоначальный, даже после повторного запуска.
Первый раунд и его отказы остаются в `rounds`; новый — в том же манифесте.
Требования к смыслу, лицензии и качеству не ослабляются. После второго отказа —
`needs_visual`. Ошибки сети, авторизации, квоты, неполный/некорректный ответ
останавливают обработку с причиной; они не запускают переформулировку.

Результат — `visual_review.json`. `--scene-id` обновляет только выбранную сцену,
остальные результаты сохраняются, в том числе при ошибке. Общий `ai_reviewed`
возможен только для всех сцен текущего плана с актуальными настройками и файлами.
Частичная проверка или изменение плана не означает готовность всего ролика.
В отчёте сохраняются все объяснения, выбранный файл, версия модели из ответа,
`usage` с входными/выходными токенами, число запросов и SHA-256 каждой
действительно переданной картинки. Ошибка API и уже полученный расход
сохраняются даже при некорректном JSON. Статус `model_reviewed` означает
проверку моделью, а не гарантию безошибочного определения вида животного.

Галерея с объяснениями ИИ собирается без дополнительных платных запросов:

```bash
.venv/bin/python review_gallery.py --manifest outputs/ИМЯ_ПАПКИ/visual_review.json --output ~/Desktop/Smartgram_penguin_vision.html
```

Для AI-отчёта галерея использует локально сохранённые изображения, которые
были отправлены модели. Она показывает текст сцены, модель, токены, все
оценки, наблюдения, отказы и кандидатов в резерве. Изображения встроены в HTML.

В реальном тесте императорских пингвинов отправлены шесть изображений одним
запросом, включая фотографию Колизея как заведомо неподходящий контроль.
Модель `gpt-4.1-mini-2025-04-14` выбрала фотографию птиц на льду и отклонила
Колизей. Расход: 2784 входных и 450 выходных токенов (3234 всего).
Результат: `outputs/vision_penguin_test_dzza41hn/visual_review.json`.
Это один реальный тест, не оценка общей точности распознавания.

Интеграция сверена с официальной документацией OpenAI:
[изображения и Vision](https://developers.openai.com/api/docs/guides/images-vision?api-mode=responses),
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

## Как выполняется проверка

1. Запрос сбора через веб-инструмент возвращает факты и вложенные фрагменты источников.
2. Запрос без веба оценивает полноту «Хватает / Не хватает». Недостающие вопросы
   могут запустить один дополнительный раунд сбора; накопленное сохраняется.
3. Только `enough=true` завершённого исследования формата 4 разрешает сценариста.
   Он получает всё исследование: факты, фрагменты, ссылки, оговорки, противоречия.
   Исторические форматы исследований можно просматривать, но для нового реального
   сценария нужен результат двухшагового исследователя «Хватает».
4. Первый запрос без веба создаёт один объект `fragments`. Второй запрос с вебом
   проверяет всю версию: factual text и соответствие visual. Он должен читать
   подтверждающие материалы, не принимать сниппет или саму ссылку за доказательство.
   Один качественный источник достаточен для одного утверждения. Это модельная
   проверка, требующая критического просмотра человеком. Локальный код проверяет
   структуру ответа, индексы, поля, точность проблемных фраз и согласованность вердикта.
5. `approved=true, issues=[]` означает «Можно использовать»; `false` с конкретными
   замечаниями — «Нужно исправить». Ошибки API, JSON, индексов и веб-инструмента —
   технический сбой, без ложного одобрения. Доступные действия веба и источники
   сохраняются буквально из API; наличие URL не выдаётся за открытие страницы.
6. При замечаниях автор получает весь предыдущий сценарий и все проблемы text/visual.
   Новая версия проверяется целиком. По умолчанию допускаются первый вариант и две
   доработки; `SCRIPT_MAX_REVISIONS=0` оставляет только первый вариант с проверкой.
   В `script_state.json` хранится один общий счётчик для содержательных замечаний
   и правок после измерения аудио. Возобновление не обнуляет бюджет. Технический
   сбой автоматически не перезапускается. Сохранённые настройки бюджета сохраняют
   силу при продолжении; изменение `.env` не выдаёт дополнительные попытки старому запуску.
7. Цель 30–45 с передаётся автору как ориентир. Подсчёт слов не служит отказом и
   не называется фактической длительностью. В полном конвейере после проверки текста озвучки код
   измеряет WAV. При выходе за диапазон передаёт фактическое время сценаристу,
   использует оставшийся общий бюджет, заново проверяет текст и генерирует озвучку.
8. Из одобренных fragments Python получает `narration_text`, соединяя только `text`
   через пробел. `visual` в TTS не попадает. Выбранный синтезатор (сейчас Gemini TTS) создаёт общую дорожку. Адаптер
   в `scene_planner.py` без модели готовит `scenes.json` для существующего подбора:
   один фрагмент → одна запись, text → narration, visual → описание и начальный запрос.
   Точные границы после успешной озвучки хранятся в `audio_manifest.json`: OpenAI
   выбирает word_id из Deepgram, Python получает секунды из сохранённых слов.
   Деление по словам или поровну не используется.
9. Подбор Commons и Vision по-прежнему проверяют реальные файлы, лицензии и смысл.
   Они не переписывают произносимый текст. Версия сценария входит в ключи кеша и
   манифесты; устаревшие материалы не выдаются за актуальные. Исходные исследования
   и старые запуски не удаляются. Старые текстовые сценарии просматриваются, но им
   не придумываются visual: для продолжения создайте новый сценарий по исследованию.

### Контракт и команды сценариста

Ответ автора содержит только:

```json
{"fragments":[{"text":"Текст диктора.","visual":"Что показать."}]}
```

Число фрагментов не фиксировано; пустые поля и дополнительные свойства запрещены.
Модель не возвращает полный дублирующий текст, таймкоды, файлы или якобы найденные
изображения. `narration_text` и `script_version_id` вычисляет Python и сохраняет отдельно.

Первое произносимое предложение обозначает явление и смысл объяснения без
заголовка. По умолчанию это короткий конкретный вопрос, сразу переходящий в
объяснение; столь же понятное начало без вопроса тоже допустимо. Начало остаётся
в первом фрагменте, его visual сначала знакомит с объектом, затем с устройством.
Промпт исключает пустые вступления, повторное объяснение одного механизма и
необязательные усложнения, сохраняя существенные оговорки. Существующий второй
запрос оценивает понятность начала по смыслу и при проблеме возвращает обычное
замечание к фрагменту 0, полю text или visual. Отдельных этапов, поля hook,
проверки по вопросительному знаку и дополнительных вызовов модели нет.

Только сценарист и его проверка из сохранённого исследования:

```bash
.venv/bin/python main.py --research-file outputs/ПАПКА/research.json --stop-after script
```

Три постоянные темы из готового набора исследований, без повторного поиска,
озвучки и подбора изображений:

```bash
.venv/bin/python script_batch.py --research-batch outputs/research_batch_cecdglkj
```

Команда создаёт `outputs/script_batch_.../report.html` и автоматически передаёт
его в Smartgram Review через Google Drive для компьютера. Неудача одной темы
не скрывает остальные. Отчёт содержит все версии, полный текст, visual, проверки,
исходное исследование с путём/датой, полные запросы/ответы, модели, usage,
раскрытые веб-действия, время и ошибки. Неизвестные поля и стоимость не заменяются нулём.

Продолжить сценариста в той же папке, сохраняя бюджет (завершённый результат
переиспользуется; после технического сбоя повторных запросов не будет):

```bash
.venv/bin/python main.py --resume-script outputs/ПАПКА_СЦЕНАРИЯ
```

`--dry-run` сохраняется. `run_scriptwriter(..., duration_feedback={
"measured_duration_seconds": ...})` — вход для доработки по готовому аудио;
в полном конвейере он вызывается автоматически по измерению WAV.

Настройки в `.env` соответствуют схеме сайта `schema_version=5`,
`architecture=research-script-visual-v1`. Импорта сайта в проекте нет;
новый сервер или интеграция сайта не создавались. Сайт не менялся.

| Настройка | По умолчанию |
| --- | --- |
| `SCRIPT_WRITING_MODEL` / `SCRIPT_VERIFICATION_MODEL` | `gpt-6-luna` / `gpt-6-luna` |
| `SCRIPT_WRITING_REASONING_EFFORT` / `SCRIPT_VERIFICATION_REASONING_EFFORT` | `medium` / `medium` |
| `SCRIPT_WRITING_TIMEOUT_SECONDS` / `SCRIPT_VERIFICATION_TIMEOUT_SECONDS` | `120` / `180` |
| `SCRIPT_WRITING_MAX_RETRIES` / `SCRIPT_VERIFICATION_MAX_RETRIES` | `0` / `0` |
| `SCRIPT_VERIFICATION_MAX_TOOL_CALLS` / `SCRIPT_VERIFICATION_CONTEXT_SIZE` | `8` / `medium` |
| `SCRIPT_TARGET_MIN_SECONDS` / `SCRIPT_TARGET_MAX_SECONDS` | `30` / `45` |
| `SCRIPT_MAX_REVISIONS` | `2` |
| `SCRIPT_WRITING_PROMPT_FILE` | `prompts/script_writing.txt` |
| `SCRIPT_VERIFICATION_PROMPT_FILE` | `prompts/script_verification.txt` |

Оба промпта редактируются в обычных текстовых файлах; путь можно заменить через
настройки. Технические повторы отключены по умолчанию; их включение — явная
настройка SDK, не новая содержательная доработка. Журнал хранит количество
логических вызовов SDK и транспортную настройку; число внутренних сетевых
попыток при ненулевом SDK retry API отдельно не раскрывает. Модель при ошибке
не подменяется, искусственного `max_output_tokens` нет. `OPENAI_MODEL` и
`OPENAI_VISION_MODEL` остальных потребителей сохранены.

В исторических запусках `completed_to_assets` в журнале означает завершение подготовки и проверки моделью до ручного просмотра,
`needs_visual` — что часть визуальных материалов ещё не подготовлена,
`demo_completed` — тестовый проход, `stopped` — остановку с причиной.
Исходное `fact_check_status: not_performed` исследования относится к моменту
исследования: последующая проверка сценария находится в `verification.json`.
Перед продолжением проверяются `warnings`, `blocking_issues`, `topic_assessment`,
исторические `limitations` (если присутствуют), общий список `sources` и
URL/заголовки источников каждого факта, даже для
`insufficient_data`. Повреждённый файл вызывает понятную `ResearchError`
с названием поля до сохранения Markdown и вызовов следующих этапов.
При ошибке API сохраняются уже готовые этапы и причина в журнале.
При ошибке записи на диск один из файлов мог успеть сохраниться частично.

Код завершения: `0` — план или завершённый запуск (готовность материалов — по
статусам манифеста), `1` — ошибка или остановка,
`2` — неверные аргументы. Остановка в демонстрации `fail`, `unavailable`
или `insufficient` с кодом `1` — ожидаемый результат.

## Просмотр одного запуска

Технический адаптер использует `material_type=image`; отдельного ИИ-планировщика нет.
`AVAILABLE_MATERIAL_TYPES=image` сохраняет возможность будущего расширения до
`image,video`. Подбор видео пока не реализован: в старом плане уже запрошенное
видео не заменяется картинкой молча.

Страница строится по локальным материалам, без сетевых запросов:

```bash
.venv/bin/python result_page.py --run-directory outputs/ИМЯ_ПАПКИ
open outputs/ИМЯ_ПАПКИ/result.html
```

Она отдельно показывает предупреждения и блокирующие проблемы исследования.
Если сценария ещё нет, проверка обозначается «Проверка не запускалась».
Страница содержит полный сценарий (при остановке — последний черновик с пометкой),
источники, текст каждой сцены, выбранное изображение, объяснения и аудиоплеер.
WAV и изображения встроены в HTML. Общая длительность повторно измеряется по
WAV, а не берётся из оценки сценария. При незавершённой озвучке показаны сумма
уже созданных файлов и число озвученных сцен. Отсутствующие этапы не имитируются.

## Автоматические проверки

```bash
.venv/bin/python run_tests.py
```

Проверены два запроса на успешном пути сценариста, строгие fragments,
замечания к text и visual, общая история и бюджет 0/2, возобновление,
доработка после измеренного аудио, запрет downstream при ошибках и устаревших
версиях, отсутствие отдельного вызова планировщика. Исторические проверки
исследования и загрузчика источников сохраняются. HTTP-транспорт SDK и загрузчика подменяется.
Для новой речи проверяются Realtime-чанки/завершение, Deepgram, контракт и
привязки, конфликты ASR, лимиты и resume. Исторические Gemini-тесты сохранены
отдельно и не являются проверкой активного пути.
Подбор Commons проверяется с подставными ответами: поиск, лицензии, соответствие,
разрешение и повреждение файлов, кеш, отсутствие подмены видео изображением.
Тесты Vision проверяют передачу настоящих байтов в подставной HTTP-транспорт,
покрытие всех кандидатов, отказ от выбора при неопределённости/отклонении всех,
сохранение usage, лицензии и отсутствие повторных запросов. Они не подменяют
отдельный тест настоящего распознавания, описанный выше.
Проверяются также частичные отчёты, сохранение результатов при ошибке, кеш
по текстам/моделям/настройкам/хешам, история usage, лимит двух раундов после
возобновления, независимость превью от галереи и измерение WAV для страницы.
`run_tests.py` запрещает реальные подключения и DNS во всём наборе.
В автотестах платных запросов нет: они проверяют управление конвейером
и форматы данных, а не качество настоящей речи, сценария или содержимое
реальных веб-страниц. Результат отдельного сетевого теста Commons описан выше.

API-интеграция сверена с официальной документацией OpenAI:
[веб-поиск](https://developers.openai.com/api/docs/guides/tools-web-search),
[Structured Outputs для Responses](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).
Автоматические повторы API отключены, таймаут — 120 секунд на запрос.

## Архив и HTML-отчёты для Google Drive

Готовые отчёты также копируются в папку `Smartgram Review`, настроенную через
`SMARTGRAM_REVIEW_SYNC_DIR`. Команды `research_batch.py`, `research_report.py`,
`result_page.py`, `review_gallery.py`, `script_batch.py` и `voiceover_batch.py` передают итоговый HTML автоматически.
Набор исследований передаёт общий отчёт один раз после обработки всех тем;
промежуточные снимки не отправляются. Это не запускает новые API-запросы.

Чтобы передать уже существующий отчёт или страницу, созданную программно:

```bash
.venv/bin/python html_report_sync.py --report outputs/research_batch_cecdglkj/report.html
```

Передаётся только выбранный автономный HTML. Содержимое `outputs` целиком,
тексты локальных настроек и ключи не копируются. Проверяются маркер папки,
UTF-8, отсутствие известных форматов ключей и значений секретных настроек из `.env`.
Изображения и аудио в наших страницах встроены в HTML; для стороннего HTML
с локальными зависимостями сначала подготовьте автономную страницу.

HTML сначала записывается во временный файл, проверяется по размеру и SHA-256,
затем атомарно получает имя `Smartgram_report_ВРЕМЯ_НАЗВАНИЕ.html` (UTC).
При совпадении имени добавляется номер. Старые версии сохраняются; повторная
передача неизменного отчёта переиспользует исправную копию. После копирования
атомарно обновляется `reports.json`: список версий с размерами, SHA-256 и
`latest_report_name`. Архивный `latest.json` относится только к ZIP и не меняется.
При ошибке сохраняются исходный HTML и прежний список; сообщение объясняет сбой,
команда возвращает `1`. Если папка не настроена, HTML остаётся локально,
команда сообщает об отсутствии передачи и также возвращает `1`.

В отдельном чате ChatGPT можно попросить:

> В папке Smartgram Review найди reports.json и открой HTML по latest_report_name.
> Если нужен другой отчёт, покажи список reports. Не подменяй отсутствующую версию.

Локальное копирование не подтверждает завершение облачной синхронизации.
Проверьте состояние Google Drive в строке меню macOS. Автоматического расписания
и наблюдателя нет: передачу запускает создание отчёта или указанная команда.
Чистые функции `build_*` и `render_*` сами файлы в Drive не отправляют;
после их ручного использования запустите `html_report_sync.py`.

Проверки без сети: `.venv/bin/python -m unittest -v test_html_report_sync`.

После каждой завершённой итерации с изменениями и проверок выполняйте обычную команду:

```bash
.venv/bin/python build_review_archive.py
```

Она создаёт и проверяет `~/Desktop/Smartgram_review.zip`, затем автоматически
копирует только этот ZIP в настроенную папку Google Drive для компьютера.
Drive API, расписание и фоновый наблюдатель не используются. Синхронизация
всего рабочего стола или документов не включается.

Настройка находится в локальном `.env`:
`SMARTGRAM_REVIEW_SYNC_DIR` — подтверждённый **абсолютный путь** к уже существующей
папке `Smartgram Review` в «Мой диск». На macOS путь зависит от аккаунта и настроек
Google Drive; его нужно брать из реально найденной папки, а не угадывать.
В `.env.example` значение намеренно пустое. Личный путь не включается в архив.

Целевая папка: [Smartgram Review](https://drive.google.com/drive/folders/13oz6ksdcwq8o63i67fKZcbOaOxGmoCtR).
При **каждой** передаче проверяется существующий `smartgram_sync_target.json`:
поле `drive_folder_id` должно равняться `13oz6ksdcwq8o63i67fKZcbOaOxGmoCtR`.
Если папка, маркер или ID не подходят, передача прекращается; новая папка
вместо неё не создаётся, маркер не подменяется.

Порядок передачи:

1. Безопасный ZIP сначала собирается во временный файл и проверяется; только
   затем заменяет предыдущий `Smartgram_review.zip` на рабочем столе.
2. В папке Google Drive записывается временная ZIP-копия. Проверяются целостность,
   размер в байтах и полная SHA-256 относительно готового локального архива.
3. Копия атомарно получает имя `Smartgram_review_YYYYMMDDTHHMMSSZ.zip` с временем UTC.
   На macOS используется системное переименование с запретом замены (`RENAME_EXCL`),
   которое защищает и от совпадения имени в момент публикации. При коллизии скрипт
   ждёт секунду и пробует новое имя, максимум пять попыток. Старые версии не меняются.
4. Опубликованная копия проверяется снова. Только после этого атомарно обновляется
   `latest.json`, указывающий на точное имя, размер и SHA-256 этой версии.

Формат `latest.json` (имя и значения каждый раз реальные):

```json
{
  "schema_version": 1,
  "archive_name": "Smartgram_review_20261101T010000Z.zip",
  "created_at_utc": "2026-11-01T01:00:00Z",
  "size_bytes": 123456,
  "sha256": "полная SHA-256 из 64 шестнадцатеричных символов"
}
```

Файл на рабочем столе и версия в Drive содержат одинаковые байты. Архив включает
код, тесты, README, зависимости, `AGENTS.md` и безопасный `.env.example` в папке
`Smartgram/`. `.env`, настоящие ключи, другие секреты, `.venv`, `.git`, кеши
и `outputs` исключаются по прежним правилам. При сборке проверяются известные
форматы ключей; секретные настройки в примере допускают только заглушки.

При ошибке передачи исправный ZIP на рабочем столе сохраняется, скрипт возвращает
`1` и не сообщает об успешной передаче. Предыдущий `latest.json` и старые версии
не удаляются. Если ошибка возникла при обновлении указателя, новая проверенная
ZIP-копия может остаться в папке без ссылки из `latest.json`; это не считается
завершённой передачей. Автоматической очистки прежних архивов нет.
Если настройка пустая, сборка сохраняет ZIP локально, явно сообщает, что передача
не настроена, и возвращает `0`.

Отдельная локальная проверка, которая **не передаёт** файл в Google Drive:

```bash
.venv/bin/python build_review_archive.py --output /tmp/Smartgram_review.zip --no-sync
```

Для обычной финальной сборки `--no-sync` не используется. Параметр `--output`
меняет путь локального ZIP, но без `--no-sync` передача остаётся включённой.

**Локальная копия не является подтверждением загрузки в облако.** Скрипт не

без дублей. При ошибке чтения Costs сохраняются прежние данные с текущей ошибкой,
не нулевыми расходами. Пустой ответ, явные нулевые начисления и ошибка различаются.

Журналы исследователя и сценариста расширяются в прежних `*_usage.json`.
Vision и переформулировки дополняют прежний `vision_usage.json`. Вспомогательный

usage и tool_usage, подтверждённые оплачиваемые единицы, раскрытые инструменты, реальные HTTP-попытки, ошибки и длительность.
Секретов и заголовков авторизации там нет. Сбой записи аналитики не отменяет ответ
генерации. Кеш не считается новым платным запросом. Неизвестный расход или usage
не превращается в ноль; reasoning уже входит в output tokens.

Денежные суммы всегда из Costs API. Стоимость вызова — только **распределение**
части суточной статьи по сверенным единицам её категории. Для неполной истории
подтверждённые единицы получают долю `сумма Costs × единицы вызова / полный объём Usage`;
неизвестный остаток не распределяется между известными вызовами. Неполнота
несвязанной категории и ненаблюдаемый повтор не блокируют подтверждённую долю,
но не позволяют объявить всю стоимость вызова известной. Модели, режимы,
input/output/cache и инструменты не смешиваются. `allocation_complete=true`
появляется только при полном денежном составе; частичная сумма остаётся false.
`Распределено + Не распределено = Из биллинга` проверяется отдельно по валютам.

Оплачиваемые поиски берутся из `tool_usage.web_search.num_requests`, а не из
числа web_search_call, открытых страниц или ссылок. Сверка идёт с Web Search Usage
и совместимой статьёй Costs. Для общей статьи требуется однородная группа;
неизвестные единицы, неоднозначная размерность quantity/unit или смешанные
режимы оставляют остаток с причиной. Старые raw-ответы и дополняющие копии
восстанавливают время/tool_usage с provenance; нынешний ключ старым вызовам
без доказательства не назначается. Реальные журналы из `.isolated/*/work/outputs`
также читаются и дедуплицируются без переноса кода параллельной копии.

Экспорт сохраняет `schema_version=1`, `source`, `allocation_details`, `calls`,

`visual_materials.json` новой схемы 2 содержит `fragments[].shots[]`: shot_id,

Запросы обычно состоят из 1–4 слов, английский основной. После неудачного

запрещены автоматически. Для схем можно отключить зум. Выбор получает реальные

Проверки страницы/прав отдельно ограничены 6 логическими GET на раунд.

При maxlag/cirrussearch-too-busy-error, 429, 5xx и тайм-ауте учитывается

## Сборка трёх роликов из уже готовых материалов

`production_batch.py` принимает явный JSON `entries`: у каждой темы `name`, `topic`,
`script_file`, `audio_manifest`, `materials_file`. Пути могут быть абсолютными.
Сценарий должен иметь сохранённую успешную проверку, аудио — принятую проверку
текста и корректные слова/таймкоды, изображения — оригиналы и доказательства одобрения.
Совместимость проверяется по script_version_id и хешам. Диагностическая озвучка
не выбирается по имени папки или дате.

```bash
.venv/bin/python production_batch.py --inputs-file outputs/assembly_existing_20261101/inputs.json --output outputs/assembly_existing_20261101
```

Эта команда запускает только монтаж и существующие стадии `subtitle_segment` /
`final_check`. `assembly_inputs.json` закрепляет входы и запрещает новый поиск,
генерацию и TTS даже при замечаниях финальной проверки. Темы выполняются независимо;
повтор команды сохраняет лимиты и использует готовые проверенные MP4, silent.mp4 и
совместимые сохранённые ответы. Текст OpenAI остаётся источником субтитров, ошибки
распознавания не подменяют его. Переносы считаются по реальному шрифту; слишком
широкий блок делится только по доказанной границе слов с исходными таймкодами.
Слова, размер шрифта и ограничения читаемости не ослабляются.

`visual_sequence.py` строит последовательность первых появлений по ID и хешам
исходников до кропа: A,A,B → A,B; A,B,A → A,B, где B продолжается до конца речи.
Один участок может охватывать несколько фрагментов диктора. `montage_plan.json`

Это новая монтажная адаптация с собственной финальной проверкой. В будущих

исходника в пределах ролика; другой кроп или перекодировка не обходят запрет.

и история. Параметры прежние: 1080×1920, 30 fps, H.264/AAC, без музыки, полный звук.
Проверки включают ffprobe, полное декодирование, громкость, расписание изображения
и субтитров, отсутствие повторов и рассмотрение кадров финального видео.

## Автоматическая замена кадра после финальной проверки

Для **нового полного запуска** интерфейс прежний:

```bash
.venv/bin/python -u main.py --topic "Кто такой Наполеон?"
```

Эта команда платная и выполняет весь конвейер. В итерации исправления она не

`outputs/research_mtyeiymq` использован только для чтения и не продолжался.

В активном FastMaterials (V3) финальное замечание теперь запускает адресный ремонт:

- `visual_repair.py` находит фактически показанный исходник по frame/cue и
  `montage_plan.json`, включая объединённые участки. Неоднозначная привязка даёт
  ошибку, а не догадку. Исправные кадры того же фрагмента сохраняются.
- `repair_id` связывает версию сценария, хеш проверенного видео, затронутые shot_id
  и нормализованное замечание. Байты кандидата проверяются по хешу. Новый ресурс
  записывается один раз, до сетевых вызовов; resume использует прежний ID и счётчики.
- Существующий планировщик получает исходный текст, прежний план, problem/correction
  и отклонённый материал. Он обновляет только visual_task, queries, критерии и
  creation проблемных кадров. Текст, shot_id, границы, сценарий и звук не меняются.
- Контекст ремонта передаётся в выбор превью, проверку кропа и генерацию. Оценки
  имеют версию задания/repair_id. Отказавший исходник учитывается по ID и хешам до
  кропа и не возвращается в тот же показ под новым именем; глобального бана нет.
- Сначала проверяется свободный кеш, затем новые запросы Pexels/Commons в прежнем
  порядке. У ремонта собственные раунды, continuation, preview_ids и бюджеты;
  заполненный первоначальный раунд больше не переоткрывается. Исходные расходы,
  операции и usage сохраняются в том же журнале.
- Генерация использует отдельный лимит, заполненные найденные финалисты её не
  блокируют. Максимум две попытки на кадр; вторая только по конкретному замечанию.
  Неизвестный исход платного запроса не повторяется. Успешная генерация кешируется
  даже при сбое последующей проверки. Геометрия прежняя: native 1024×1536, увеличение
  до 1,25, crop 1080×1920; фотографии и лицензии проверяются как раньше.
- После замены повторяется необходимый монтаж и финальный контроль актуального
  видео. WAV, ASR и совместимая разметка субтитров переиспользуются. Отзыв одобрения
  записывается до изменения публичного манифеста. Сбой между записями не возвращает
  старую готовность. Производные превью ремонта имеют отдельные пути.

Лимиты находятся в `visuals_editing_config.json` → `visuals.repair`:
`max_repairs_per_fragment=2`, `search_rounds_limit=2`, `cards_per_round=50`,
`previews_per_round=10`, `max_search_api_calls_per_fragment_per_round=6`,
`finalist_limit=3`. Это **дополнительный** ресурс одного ремонта исходного фрагмента;
обычный поиск не обнуляется. Настройки сохраняются в job ремонта. Генерация берёт
`visuals.generation.max_attempts_per_shot` (не более двух), модель и quality сохранены.
Общий предел финальных доработок остаётся `editing.final_check.max_correction_rounds`.
Ремонт не требует дополнительного ручного подтверждения внутри будущего запуска.

Ошибка сервиса/пауза сохраняет первичное сообщение, включая код поставщика, и не
маскируется исчерпанием бюджета. При нехватке ресурса JSON указывает использованные
карточки, превью, оригиналы и раунды относительно лимита. Для отвергнутой генерации
сохраняются конкретные причины. `progress.py` печатает начало, завершение, время и
редкий статус ожидания; дополнительных API ради статуса нет. Готовый MP4 выводится
явным путём. Защита от одновременных запусков сохранена.
